D. Failure handling:
  - Stop immediately on migration/import/promotion/deployment errors. Do not
    continue to the next step or environment until the cause is resolved.
  - Importers and promotion can partially succeed across records. Preserve logs
    and reports, resolve the cause, then rerun the same frozen inputs. Promotion
    retries need fresh report directories. Review existing approvals/skips.
  - Promotion before.json is a record snapshot, not an automatic rollback tool;
    it does not replace the pre-migration database/Storage backup. Failed records
    can leave unreferenced uploads; do not delete objects without checking usage.
  - Redeploy the recorded previous app only after confirming it works with the
    current schema and grants. App rollback does not undo migrations or data.
  - For incompatible schema or incorrect data, keep maintenance active and use
    the rehearsed restore procedure or a reviewed corrective migration/data fix.
    Preserve legitimate writes made after the backup when planning recovery.
    Do not reset/seed PROD, restore the local DB over it, delete applied migration
    history, or restore the DB without considering associated Storage objects.
  - After recovery, repeat migration-history, public/admin and permission checks
    before reopening service or resuming the release.


E. Storage backup (run during B.0 and C.0, before releasing the write pause):
  1. Configure tools and source access
      Install rclone and psql. Keep the backup_dir from the current DB backup.
      In the SOURCE project's Dashboard, obtain its Storage S3 endpoint, region
      and S3 access credentials. S3 credentials are not the Supabase secret key.
      Configure a separate rclone S3 remote for each source using:

      rclone config

      Name the remotes gymory-dev and gymory-prod. Select S3 / Other, disable
      environment authentication, and enter the matching project's S3 key,
      secret, endpoint and region. Keep the local rclone config private.
      For DEV only:
        storage_source="gymory-dev"
      For PROD only:
        storage_source="gymory-prod"
      Confirm the configured endpoint matches the project linked for the DB dump.

  2. Download and verify actual image files
      Pause Storage uploads/deletes as well as database writes until backup ends.
      Use a new, empty backup directory; never reuse an earlier backup destination.

      mkdir -p "$backup_dir/storage/equipment-images"
      rclone copy "${storage_source}:equipment-images" \
        "$backup_dir/storage/equipment-images" --metadata
      rclone check "${storage_source}:equipment-images" \
        "$backup_dir/storage/equipment-images" --download
      rclone lsjson "${storage_source}:equipment-images" --recursive --files-only \
        > "$backup_dir/storage/equipment-images-manifest.json"

      Require successful exit codes, including the byte-content check. Do not
      use sync: copy does not delete files. A zero-object bucket is valid only
      after confirming it is genuinely empty on the intended source project.

  3. Save bucket configuration and object metadata
      Obtain the SOURCE database connection from Dashboard > Connect (direct or
      session pooler, not transaction pooler). Use a private libpq service entry
      named gymory-dev-backup or gymory-prod-backup in ~/.pg_service.conf, with
      sslmode=require, and a matching private ~/.pgpass entry (chmod 600).
      Do not put passwords in command arguments, shell history or the repository.
      Set the matching source service; this does not change CLI linking:
        source_db_service="gymory-dev-backup"
      Or, for PROD only:
        source_db_service="gymory-prod-backup"

      psql "service=$source_db_service" -X --set ON_ERROR_STOP=1 \
        --command "COPY (SELECT id,name,public,file_size_limit,allowed_mime_types FROM storage.buckets WHERE id='equipment-images') TO STDOUT WITH CSV HEADER" \
        > "$backup_dir/storage/equipment-images-bucket.csv"
      psql "service=$source_db_service" -X --set ON_ERROR_STOP=1 \
        --command "COPY (SELECT name,metadata FROM storage.objects WHERE bucket_id='equipment-images' ORDER BY name) TO STDOUT WITH CSV HEADER" \
        > "$backup_dir/storage/equipment-images-objects.csv"

      These CSV files describe bucket settings, object paths and content metadata;
      they are reference inputs, not a complete clone of Storage internals.
      Save custom Storage policies separately if the recovery target needs them.
      Copy the complete DB + Storage backup directory to durable private storage.
      Record successful verification and source project before resuming writes.

F. Isolated restore rehearsal (never run against existing DEV or PROD):
  1. Prepare a disposable Supabase project
      Create a separate private project with a compatible Postgres version and
      required extensions. Do not deploy the application or enable background jobs.
      Its public schema must contain no app tables. Do not apply app migrations
      before importing public-schema.sql; doing both creates duplicate objects.
      Prepare any external schema/role dependencies referenced by the dump first.
      If objects already exist or dependencies are missing, stop and prepare a
      fresh rehearsal target; do not add DROP/CASCADE commands to bypass errors.

      Configure a private libpq service gymory-restore-rehearsal and its password
      as in E.3, pointing only to this disposable project. Independently check its
      host/project ref differs from BOTH DEV and PROD before executing psql.
      Select the backup directory to test (replace the example with an existing
      completed backup, not a newly generated timestamp):
        restore_backup_dir=".cache/db-backups/dev-YYYYMMDD-HHMMSS"

  2. Restore public structure and data in one transaction
      psql "service=gymory-restore-rehearsal" -X \
        --single-transaction --set ON_ERROR_STOP=1 \
        --file "$restore_backup_dir/public-schema.sql" \
        --command "SET session_replication_role = replica" \
        --file "$restore_backup_dir/public-data.sql" \
        --command "SET session_replication_role = origin"

      Replica mode prevents importer/derived-data triggers from firing again.
      It also bypasses FK triggers during load: validate relationships explicitly
      afterwards. Require a successful exit; an error rolls back this transaction.
      If the connection cannot set replica mode, stop and resolve restore access.
      Do not continue by loading data with application triggers enabled.

  3. Restore migration history only into an empty history schema
      Inspect the rehearsal target's supabase_migrations schema first. If absent:

      psql "service=gymory-restore-rehearsal" -X \
        --single-transaction --set ON_ERROR_STOP=1 \
        --file "$restore_backup_dir/migration-schema.sql" \
        --file "$restore_backup_dir/migration-history.sql"

      If definitions already exist, compare with migration-schema.sql and only load
      history data when compatible and empty. Do not clear or overwrite history
      in any existing environment. For the compatible, empty existing schema only:

      psql "service=gymory-restore-rehearsal" -X \
        --single-transaction --set ON_ERROR_STOP=1 \
        --file "$restore_backup_dir/migration-history.sql"

  4. Restore images through Storage, not SQL inserts into storage.objects
      Recreate equipment-images in the rehearsal Dashboard using the saved bucket
      settings (public flag, size limit, MIME allowlist). Configure another rclone
      S3 remote gymory-restore-rehearsal using ONLY that project's S3 credentials.
      Verify its endpoint differs from both source projects. Copy then byte-check:

      rclone copy "$restore_backup_dir/storage/equipment-images" \
        "gymory-restore-rehearsal:equipment-images" --metadata
      rclone check "$restore_backup_dir/storage/equipment-images" \
        "gymory-restore-rehearsal:equipment-images" --download

      Uploads create fresh Storage object records. Do not replay source internal
      object IDs. Compare paths, sizes and Content-Type against the saved metadata;
      correct Content-Type through supported Storage/S3 uploads if needed.
      Recreate required custom Storage policies from reviewed source definitions.

  5. Acceptance and recovery record
      Compare per-table counts with counts recorded at source backup time; capture
      those counts through the source SQL editor while writes are paused. Check
      representative gym, equipment, assignments and image-path relationships.
      Verify no orphan foreign-key references; replica mode did not validate them.
      Compare grants/RLS against the source definitions, including denied access
      to restricted fields and successful authorized admin reads.
      Verify public official images work, manual URLs remain private, and files
      match the rclone byte checks. Run application smoke tests with credentials
      pointing only to the rehearsal project. Record project ref, backup path,
      commands, outcomes, dependencies and recovery duration with the release.
      A failed rehearsal blocks deployment until the backup/restore gap is fixed.
      This rehearsal does not authorize switching production to the restored
      project: Auth, configuration, URLs and post-backup writes need a separate
      recovery plan. Keep the verified backup after removing the disposable target.
